# xp-proxy 性能测试与结果治理合同

本文细化 [SPEC.md](../SPEC.md) 的 `REQ-PERF-*`。

实现与证据状态见 [IMPLEMENTATION.md](../IMPLEMENTATION.md)，设计讨论见
[PERFORMANCE-DESIGN.md](../PERFORMANCE-DESIGN.md)。

## 目标与范围

性能工作必须解决默认配置的并发准入错误，并定位小请求延迟、吞吐和 CPU 效率差距。提高 `max_connections` 只能作为诊断对照，不能作为语义修复或默认配置验收。

性能测试不替代锁定 Xray/Mihomo 的互操作测试，不授权发布、合并或部署。

轻量和全量统一使用 GitHub-hosted Linux runner，不调用 Agent VM。客户端、被测程序和源站为同
runner 上的独立进程；三个被测程序串行交替运行，轻量按 3 轮轮转起始位，全量按 2 轮反向顺序。

CPU 分配必须依据实际可用资源记录，不假定独占物理核心；压测端、源站及共享环境的限制必须可见。

## 对照身份与构建产物

- 三个对照为候选 xp-proxy、main xp-proxy 和 Xray `26.3.27`，报告使用正式名称。配置变体必须明确实际参数和请求并发数，不能混为另一程序名称。
- 建立测试请求时锁定准确候选 SHA 和当时 main SHA。运行期间 main 更新不更换基线；新请求重新锁定 main。PR 不以其他目标分支或最近 release 替代 main。
- main 测试的候选与基线 SHA 相同时，明确标为相同版本，不宣称独立回归对照；继续提供功能、Xray 对照和资源结果，不因重复身份停止主干测试。
- 每次同场重新测量对照程序；历史数值只作趋势参考，不直接替代当前 runner 的测量。
- 独立上游构建任务产出所需架构的优化版 xp-proxy，不依赖完整 Web、xp、xp-ops 或其他架构发布构建。性能工作流不编译候选、基线或压测工具；需要编译的工具也由上游准备。
- 构建 manifest 至少绑定仓库、代码 SHA、目标架构/ABI、profile、toolchain、构建配置、二进制 SHA256、生产 workflow/run/attempt 和
  artifact 身份。

候选/main 构建配置必须可比，Xray 及配置固定并记录。

- 性能执行只消费身份匹配的产物。缺失或过期交由上游提供，不在性能 job 临时编译、不选择“最近成功”或错误 SHA 的产物。所有产物准备好之后启动性能执行计时。

## 测试矩阵与测量

| 项目     | 自动轻量                       | 手动全量                       |
| -------- | ------------------------------ | ------------------------------ |
| 被测方向 | xp-proxy 入站                  | xp-proxy 入站、出站            |
| 请求并发 | 1、8                           | 1、8、16、64                   |
| 负载     | 小请求延迟、持续上传、持续下载 | 相同负载，覆盖全部方向与并发档 |
| 对照     | 候选、main、锁定 Xray          | 相同三个对照                   |

两档共同检查内容完整性、错误、有效吞吐、p50/p95、CPU、内存和资源释放。

入站测试固定对端客户端，仅切换被测服务端；出站测试固定对端服务端，仅切换被测客户端。

协议固定为 TCP VLESS + REALITY + HTTP/2 XHTTP stream-one，UUID、SNI、path、XMUX、目标负载和运行资源必须等价。

必须独立覆盖默认配置的合法并发，不用人为降低并发掩盖错误。

压测器为长驻进程，不逐请求创建 curl 进程。记录预热、测量、停止发新请求和有界收尾的边界；未完成或未确认的应用数据不计有效吞吐。正常窗口停止与协议异常分别记录，不能把快速失败算成高吞吐。

内容校验不只依赖 HTTP 200；上传和下载均需证明实际 payload 完整性。

记录直连基线、源站与压测端资源、被测进程 CPU/PSS、连接/stream/FD 回收及环境诊断。

CPU 与内存先作为对照报告，不新增数值门槛；资源未释放属于失败，但不以分配器缓存未退回初始 PSS 单独断言泄漏。短测不能宣称长期稳定性。

## 固定判定

- 合法负载必须零异常失败、内容完整性通过、连接结束后资源释放。
- 对每个可比较场景，候选有效吞吐须同时达到 main 和 Xray 各自吞吐的至少 90%。小请求 p50 和 p95 相对每个对照均不得增加超过 5 ms。
- 判定单位是可比较场景在全部轮次上的配对结果：吞吐取逐轮候选/对照比值的中位数，
  延迟取逐轮 p50/p95 差值的中位数。单轮离群不构成退化证据；中位数越线才失败。
  轻量 3 轮时中位数低于 90% 等价于至少两轮低于 90%，全量 2 轮仍保留更严格的中位数（即均值）判定。
- `upload@8` 的单核 CPU 受限波动最大，每轮重复 3 次两秒采样并取中位数，逐次值写入证据；
  任一重复出现错误、样本不足或确认字节不足仍判无效。A/A 实测噪声与阈值推导见
  [docs/solutions/ci/xp-proxy-perf-aa-noise.md](../../../../solutions/ci/xp-proxy-perf-aa-noise.md)。
- 只比较有效且等价的样本。样本不足、无法完成比较或产物不匹配时明确报告非通过，不把缺失值当零，不用失败请求的时延评价成功请求性能。
- 测量与固定门槛计算由机器执行；特殊原因、作废及放行由人决定。机器不判断“历史缺陷应自动豁免”，不偷偷换配置，不反复重跑直到出现通过结果。

## 墙钟预算

| 项目         | 自动轻量 | 手动全量 |
| ------------ | -------: | -------: |
| 方案设计目标 |   240 秒 |   360 秒 |
| 超过设计目标 | 预算告警 | 预算告警 |
| 安全超时     |   300 秒 |   600 秒 |

从性能执行 job 的首个 step 计至证据上传结束，包含 checkout、下载、验证、准备、预热、负载、收尾与任何重试；排队和上游构建等待不计入。

预算超出不直接等于性能数值失败，安全超时则报告执行超时。必须保存阶段耗时，不能只报告采样秒数冒充总墙钟。

具体采样窗口是需要实测的工程设计，不是已经完成的证据。若预算内无法获得可靠数据，必须明确报告设计目标尚未达到，不能删减合同矩阵或放宽门槛后宣称完成。

## 自动触发与合并门禁

PR 和 main 上影响 xp-proxy 的变更自动运行轻量测试。

保守路径集合覆盖协议 binary/core、共享代码、相关 manifest、根 Cargo.lock、工具链、构建配置、性能脚本、fixture 和工作流；纯文档、Web 和无关控制面变更明确报告
不适用。

路径规则必须有覆盖测试。

自动门禁固定命名为 `xp-proxy-perf-gate`，只依据当前 PR 候选的自动轻量结果与当前人工豁免状态。旧 SHA、旧 attempt 或另一个 workflow 的结果不能解锁新候选。

手动全量独立报告，不自动修改 PR 必需门禁。

| 条件                     | 性能测试执行 | PR 性能门禁       | 原始测量结果         |
| ------------------------ | ------------ | ----------------- | -------------------- |
| 无豁免、轻量通过         | 正常         | 通过              | 保留                 |
| 无豁免、失败/错误/未完成 | 正常         | 非通过            | 保留                 |
| 存在 `perf:waive`        | 仍正常执行   | 人工豁免 `waived` | 保留真实状态         |
| 无关变更                 | 不启动负载   | 明确不适用        | 不伪造测试通过       |
| main 相关变更            | 正常执行     | 不继承 PR 豁免    | 保留该 main SHA 结果 |

`perf:waive` 持续作用于该 PR，去标后恢复正常门禁。加标/去标需要重新评估门禁，不要求重新执行完整负载；标签不停止、取消或跳过测量，不修改数据有效性，也不影响其他 CI。

原始测量检查与必需门禁分离，避免重复强制原始测量成功使豁免失效。

## 人工结果标记

三个状态分别保存：`measurement` 为真实测量结论，`merge_gate` 为合并门禁结论，`disposition` 为人工有效性决定。

默认分支提供手动入口 `xp-proxy-perf-result`：

| 输入                 | 合同                                           |
| -------------------- | ---------------------------------------------- |
| `action`             | `invalidate` 或 `restore`                      |
| `target_run_id`      | 本仓库性能测试的准确 run ID                    |
| `target_run_attempt` | 准确 attempt，不能只写“最新一次”               |
| `reason`             | 必填人工理由，不由机器判断是否足够构成性能问题 |

入口核对目标并解析 SHA、profile、构建目标与产物标识。

人工记录至少包含 repository ID、目标 workflow/run/attempt、SHA、profile、target、产物校验和、操作者、理由、时间和操作 run 链接。

以 `repository_id + run_id + run_attempt` 区分结果，重新运行同一 run 不覆盖另一个 attempt 的有效性。

作废与恢复追加记录，不改写原始测量或删除历史操作。对同一目标按成功提交的操作序列解释当前状态，避免并发操作乱序。

恢复只撤销人工排除，不把失败变成通过；作废只影响选中的结果，不禁测整个 SHA，也不自动作废同 SHA 的新 run。

独立 Check 使用明确的 XP 名称展示当前状态，关联被测 SHA、目标 run/attempt 和人工操作链接。

`invalidated` 是本项目字段，不伪造 GitHub 原生 conclusion。原 Actions run 仍保留原始状态，不能承诺原页面红叉消失或已完成 summary 被改写。

**人工操作的依据是指定默认分支手动工作流实际生成的结构化操作记录，Check 是展示。

** 读取端必须核对仓库、workflow 身份、执行 ref/revision、手动事件、run/attempt、对应操作产物及内容一致性。

名称、`app=github-actions`、可填写的 `external_id` 或一个自报链接都不能单独证明来源；无法核对的同名记录不生效。

标记入口不得执行待审 PR 代码，写标记权限与负载执行隔离。

后续汇总、历史趋势及任何结果复用须排除已人工作废结果，展示理由。作废不等于 PR 豁免；缺少有效对照而希望合并时，人需独立使用 `perf:waive`。

不自动退回旧 main、release 或其他看起来正常的数据。

## 留存与缺失证据

测试结果、Check 展示、操作记录和审计证据统一按 90 天设计，遵守仓库实际留存限制并记录可用期。人工决定必须与其原始结果保持可关联；不得在作废记录过期后把仍残留的旧数据自动恢复为有效。

过期、缺失、来源无法核对或审计不完整的历史结果不再复用；查询错误不能当作“从未作废”。重新执行同 SHA 的测试允许生成新的独立结果，不要求永久保存过去测量，也不依赖本地忽略目录中的证据。

## 验收重点

实现必须证明：双档矩阵与阈值、默认并发正确性、准确产物、固定 main SHA、相关路径覆盖、加标/去标时测试继续、main push 测量、全量不改变自动门禁、invalidate/restore
操作链、同名伪标记拒绝、attempt 隔离及到期数据排除均符合合同。

性能数值、运行预算和来源校验须有实际 Actions 证据，文档通过不能替代运行验收。

## 多目标与连接拓扑验证

互操作阶段增加固定的 8 个独立目标端口，每个目标返回唯一身份和每条流独立 payload 的摘要与回显。混合使用 IPv4 地址和 localhost 域名，检查 VLESS
目标解析、目标选择及跨流数据隔离。Xray 客户端始终显式设置 `maxConnections=1`。

分别验证一个客户端的 16 条流、四个独立客户端的 64
条流，以及四客户端下的快目标、事件阻塞慢目标、拒绝连接和重置连接混合。必须在慢目标尚未释放时完成快目标业务，故障目标必须实际失败，其他流仍完整成功；慢目标释放后也必须完整返回。Linux
从实际 TCP socket 状态核对客户端到代理的底层连接数分别为 1 和 4，不能仅凭配置推断 MUX 拓扑。先对锁定 Xray 服务端验证相同
fixture，再验证候选服务端；之后才开始 Mihomo 阶段。

这些是功能隔离场景，不宣称公网多站点吞吐或全局吞吐公平性。现有 240/360 秒性能消费 job
预算不变，拓扑互操作单独计时。内存上限等单变量实验仅为临时排障，不作为交付脚本、
工作流或持续验收要求；正式比较沿用锁定运行配置。
