# xp-proxy 性能需求设计讨论

本文保存 xp-proxy 性能需求的设计讨论、事实与工程预算。

已确认的长期合同已整理到 [SPEC.md](./SPEC.md) 和 [contracts/performance.md](./contracts/performance.md)；本文件不表示工作流
、修复或运行验收已完成。

## 已确认的目标与边界

- 程序名称统一使用 `xp-proxy` 和 `Xray`。

对照配置可简称“xp-proxy（64 并发）”，但必须注明实际设置为服务端 `max_connections=64`，并单独标明实际请求并发数；不得将此前最高 16 并发的短测描述成已经通过 64
并发验收。

- 修复默认配置下的并发准入问题，并用 trace 与单变量实验定位小请求延迟、吞吐及 CPU 效率差距；提高配置上限不能替代语义修复。
- 建立可复现基准，包含直连容量基线、压测端和源站瓶颈检查、逐请求成功与内容完整性校验、有效吞吐、延迟分位数、CPU、内存与资源释放证据。

轻量和全量统一在 GitHub-hosted Linux runner 上运行，不调用 Agent VM；客户端、服务端和源站位于同一 runner 的独立进程，被测 xp-proxy 与 Xray
串行交替运行，并检查直连容量和环境噪声。

具体 CPU 分配与噪声判定尚待设计，不假定 runner 核心数或专属物理 CPU。

- 全量验证覆盖请求并发 1/8/16/64、大小请求、上传与下载；全量测试按预计总墙钟六分钟内完成来设计，必须给出场景、测量窗口和执行开销的时间分配；六分钟是方案设计预算，不是已经批准的 CI 硬超
  时或性能失败阈值。

此前“主要场景每轮至少 60 秒、重复 5 轮”和“至少 30 分钟稳定性验证”的建议被该预算取代，不再作为本套测试的验收要求。

- 修复验收目标为合法负载零异常失败、内容完整性通过、连接结束后资源释放；同条件吞吐至少达到锁定 Xray 对照的 90%，小请求 p50/p95 延迟差不超过 5 ms。

资源累积只承诺在实际测量窗口内检查，不用六分钟短测宣称长期稳定性。自动门槛遵守正式合同；具体采样实现仍需实测。

- GitHub Actions 支持自动必跑轻量性能测试与手动选跑全量性能测试；实际影响 xp-proxy 的变更自动触发，不能仅因变更未落在主 binary 目录就漏测协议核心或依赖。
- 轻量测试目标为 180 秒以内，超出标记预算告警，300 秒硬超时失败；手动全量按预计 360 秒以内完成设计，超过 360 秒记录预算告警，600 秒安全超时终止并报告执行超时，不因实际耗时超过
  360 秒就自动判定性能失败。

从性能执行 job 的首个 step 到最终证据上传结束计时，包括 checkout、产物下载、校验、准备、测试、清理及任何重试；排队和上游构建等待不计入。

性能工作流不编译程序，复用其他工作流构建的产物。

- 候选产物必须绑定准确的代码 SHA、目标架构、构建配置与校验和；缺失、过期、错误 SHA 或错误目标的产物不能替代本次候选。
- 轻量与全量均保留三个对照程序：候选 xp-proxy、主干 xp-proxy、锁定版本 Xray。

在同一次性能执行中串行交替测量，分别判断变更退化和相对 Xray 的性能差距；不使用不同 runner 或不同运行的绝对数值直接代替同场对照。

基线始终来自 `main`，测试请求建立时锁定当时的准确 main SHA，不能改用 PR 的其他目标分支、最近发布版本或不同 SHA 的可用产物。

一次运行内 main 更新不替换基线，下次新请求重新锁定。

- 在上游构建工作流增加独立的 xp-proxy 产物任务，仅构建性能测试所需架构的优化版二进制，并输出代码 SHA、构建目标和二进制校验和。

性能工作流仅消费产物，不编译，也不依赖 Web、xp-ops 及其他架构的完整发布构建。候选与变更前 xp-proxy 应使用可比的构建配置，Xray 版本及运行参数固定并记录。

- 轻量覆盖入站链路的小请求延迟、上传与下载，请求并发 1/8，并专门检查默认配置下的并发准入。全量增加出站链路及请求并发 16/64，覆盖完整矩阵。

两档均检查内容完整性、错误率、CPU、内存及连接结束后的资源释放。

- 对应场景的候选吞吐必须同时不低于变更前 xp-proxy 和锁定 Xray 的 90%；小请求 p50/p95 延迟相对两个对照均不得增加超过 5 ms。合法负载零异常失败，内容校验必须通过。

CPU 和内存先作为对比报告，不新增未经确认的数值门槛；资源未释放属于失败。有限窗口内的资源释放检查不等于长期内存稳定性证明。

- 机器按固定规则执行测量、门槛比较和环境/产物一致性检查，保留错误及诊断证据；数据不足或无法完成比较时默认不通过，不能自动反复重跑直到通过。

是否将异常结果正式作废以及是否批准例外放行，均由人明确决定；不得由机器推断历史缺陷或自动豁免。机器检测到的异常与人工确认的作废是不同状态。

- 自动触发采用保守的相关路径集合，允许少量多跑以避免漏测；包括 xp-proxy、xp-proxy-core 及其共享代码，相关 Cargo manifest、根 Cargo.lock、工具链、构建
  配置、性能脚本、fixture 和相关工作流。

纯文档、纯 Web 和无关 XP 控制面修改不触发性能执行，但统一检查入口必须明确返回“不适用”，不能因为整个工作流被路径过滤而让必需检查永久等待。具体路径清单须有触发规则测试。

- 当前工作只收敛需求和文档，不启动代码修复、工作流修改、发布或生产部署。

## 当前实测证据及限制

`v3.48.15` 的短测在一台隔离 Agent VM 内交替运行三个服务端配置，正式阶段共 54 个场景批次、2088 次请求。

默认 xp-proxy 失败 402/696；提高限制的 xp-proxy 与 Xray 各为 0/696。该结果足以暴露并发功能缺陷及延迟/吞吐差距，但不足以完成长期性能验收。

原测试客户端、被测服务端和 Python 源站共享一台 VM；每个请求新建 curl 进程，各场景顺序复用会话，且宿主 CPU 共享。正式负载合计约 274 秒，并非持续稳定性测试。

后续测试必须明确资源隔离、源站容量、场景间清理和运行时间，避免把快速失败计入吞吐，或把共享环境的波动解释为固定性能倍率。

原始本地证据位于仓库忽略的 `.run/xp-proxy-perf-20261117/`，不属于已提交的长期证据；未来 CI 证据应发布为绑定候选 SHA 的 Actions artifacts，不能
依赖该本地目录。

## 决策树与待决问题

### 工程执行预算

以下是需要实施验证的工程预算，尚未实测，不是已经达成的运行耗时。

三程序使用 A（候选）、B（main）、C（Xray）标识记录，两个 sweep 反转顺序为 A/B/C 和 C/B/A；运行报告必须展示正式程序名和精确版本。

每个程序在一个 sweep 内完成该方向全部场景，减少进程重启开销；独立场景之间必须清理活动会话和计数。

| 阶段                                            | 轻量预算 | 全量预算 |
| ----------------------------------------------- | -------: | -------: |
| checkout、产物下载、manifest 与校验和验证、准备 |    30 秒 |    30 秒 |
| 直连基线及执行环境记录                          |     6 秒 |     6 秒 |
| 进程启动、就绪和预热                            |     6 秒 |     6 秒 |
| 同场负载采样                                    |    72 秒 |   288 秒 |
| 默认配置功能检查、回收及资源检查                |     6 秒 |     6 秒 |
| 报告生成及证据上传                              |    12 秒 |    12 秒 |
| 余量                                            |    48 秒 |    12 秒 |
| 总设计预算                                      |   180 秒 |   360 秒 |

轻量负载采样为 `1 个方向 × 2 个并发档 × 3 类负载 × 3 个程序 × 2 个 sweep × 2 秒 = 72 秒`；全量为
`2 个方向 × 4 个并发档 × 3 类负载 × 3 个程序 × 2 个 sweep × 2 秒 = 288 秒`。

三类负载分别为小请求延迟、持续上传、持续下载；两秒槽必须包含停止发新请求及有界收尾，不能在每个槽之后叠加无界排空时间。正常边界停止与协议错误分开记录，未完成或未确认的数据不计有效吞吐。

压测器使用长驻进程，不逐请求启动 curl；内容生成、校验及客户端 CPU 必须计入环境余量检查。

采样不足、源站饱和或对照波动导致短窗口无法支持门槛判断时，结果必须为验证未完成，不能为了在预算内成功而删场景、降低请求并发或放宽性能门槛。

两秒窗口是否足以稳定判定、预热及准备预算是否可达，需要在实施中实测；若不可达，应报告设计预算未满足并重新讨论，不能宣称六分钟方案已验证。

### 测试执行、合并门禁与结果有效性

这三项必须独立：`measurement` 保存真实测试结论，`merge_gate` 决定本 PR 是否被性能检查阻止合并，`disposition` 保存人工是否作废某次结果。

机器不推断历史缺陷、不批准例外、不自动作废异常结果。

#### PR label 只豁免合并门禁

- 专用 label 为 `perf:waive`，持续作用于本 PR，移除后恢复正常门禁。添加或移除 label 都重新评估固定名称的门禁检查。
- 有 label 时，PR 的自动性能测试仍按正常条件启动、运行并保存真实通过/失败/错误结果；不得因 label 跳过、取消或停止测试。门禁单独显示 `waived`，允许合并但不宣称性能合格。
- 建议固定必要检查名称为 `xp-proxy-perf-gate`；原始测量检查与门禁分离，避免原始失败仍被另一条必需检查重复阻塞。其他 CI 检查不受该 label 影响。
- 有效的人工豁免不必等待性能测量成功，但不会终止已经运行的测量；结果仍可用于诊断和后续人工审阅。测试失败不能自动作废或清空 main 的记录。
- PR 的性能合并门禁只依据当前候选自动轻量测试与人工豁免状态。手动全量独立报告，不自动改变 PR 门禁；人可以根据其结果决定是否合并，不将按需全量隐式升级为另一条必需检查。

#### main 继续运行测试

- main 上发生影响 xp-proxy 的变更后，独立运行轻量性能测试并保存该准确 SHA 的结果；手动全量仍可选择 main 的准确 SHA。
- PR 的 `perf:waive` 不继承到 main，不豁免 main 测量，也不让合并后的测试停止。

候选和 main 基线 SHA 相同的测量不能宣称提供了独立的主干回归对照；仍报告功能、绝对 Xray 对照和资源数据。

- 每次 PR 测试仍需同场重新测量已锁定的 main；历史性能数值不替代同场测量。作废历史结果不能用来禁止重新测试相同 main SHA。

#### 人工将某次主干测试结果作废

- 提供默认分支上的手动 Actions 入口 `xp-proxy-perf-result`，选择 `invalidate`，输入准确的 `target_run_id`、
  `target_run_attempt` 和必填 `reason`。

入口校验目标确实为本仓库的性能测试 run，并展示其 main SHA、profile、构建目标和产物标识；不接受只写“最新一次”的模糊目标。

- 只有人通过该入口明确提交作废指令后，才记录 `disposition=invalidated`；自动化只校验身份与目标、执行记录，不判断该理由是否构成性能异常。
- 记录至少包括仓库、目标 workflow/run ID/attempt、对应 SHA、profile、构建目标、产物校验和、操作者、理由、时间和本次作废操作 run 的 URL。

保留原始日志、数值与最初测试结论，不删除或覆写它们。

- 实现建议采用独立 GitHub Check 记录作废标记：check 绑定被测 SHA，`external_id` 精确绑定目标 run/attempt，output 保存上述元数据，
  details 链接原始测试与人工操作。

`invalidated` 是本项目的结果有效性字段，不是伪造一个 GitHub 原生 conclusion；它也不改写原始测量 check。

仅该受控手动入口拥有写标记权限，执行时不运行待审 PR 的代码。

- 已确认的来源验证：独立 Check 用于展示，人工标记的依据为本仓库指定默认分支手动工作流实际生成的结构化操作记录。

读取端必须验证 workflow/run/attempt 与记录的关联，核对目标结果身份及标记内容；只验证 Check 名称、`app=github-actions` 或自报链接不足以证明具体工作流来
源。

不得信任只有同名 Check、没有可核对操作记录的标记。

- 后续报告、历史趋势、结果挑选和任何结果复用必须读取该人工标记，排除匹配的已作废 run/attempt；显示“人工作废”及理由，不能显示为性能通过，也不能在读取标记失败时静默使用该结果。
- 测试数据、作废/恢复记录与审计证据统一按 90 天设计；过期、缺失或无法核对的记录不复用，不因作废标记消失而自动恢复旧数据。实际受仓库留存策略约束。
- 作废范围仅为明确选中的测试结果，不是整个 main SHA、构建二进制或所有未来 run。同一 SHA 可重新测试，新 run 有独立结果和有效性；不会因为旧 run 作废而自动作废。
- 允许人在同一入口选择 `restore` 恢复结果有效性，同样要求准确目标与必填理由。作废和恢复都追加审计记录，保留操作者与时间，不删除之前的决定；恢复只撤销人工排除，不将原始失败改成通过。

按目标结果的最后一个成功提交的人工操作解释当前有效性，并保留完整操作链。

- 人工作废不等于 PR 豁免。缺少可用对照时，普通门禁保持非通过；需特殊合并时由人独立添加 `perf:waive`。不自动换用旧 main SHA、发布版本或其他看起来正常的结果。

### 仓库事实

- GitHub Actions 的 `GITHUB_TOKEN` 在授予 `checks: write` 后可创建 Check Run，不要求另装自建 App；多个 Actions 工作流共享
  GitHub Actions App 来源，所以 App 名称不能唯一证明指定 workflow。

[官方工作流权限说明](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)
。

- GitHub 的 Checks、workflow runs、artifacts 与日志并非永久保留；官方默认保留 90 天，实际受仓库和上级策略约束。

公开仓库可配置 1–90 天、私有仓库 1–400 天；自 2026-10-01 起统一策略也适用于 Checks 和 workflow runs。

结果及人工标记的保留策略必须一致，不能在作废标记过期后将缺少标记的旧数据自动恢复为有效。

[官方保留策略](https://docs.github.com/en/organizations/managing-organization-settings/configuring-the-retention-period-for-github-actions-artifacts-and-logs-in-your-organization)
。

- 现有 `ci-performance.yml` 与 `release-performance.yml` 衡量 CI/发布构建耗时，不是代理运行时的吞吐、延迟与内存测试；不能沿用其通过状态证明
  xp-proxy 性能合格。
- `release-build.yml` 已构建 xp-proxy 并上传 `musl-${artifact_prefix}-${suffix}` 产物，包含同包的 xp、xp-ops；构建
  checkout 会校验目标 SHA。

当前普通 CI 没有上传可直接消费的 xp-proxy 可执行文件。

- 现有发布构建链路带 Web、其他程序和多架构工作；已决定增加更窄的独立上游 xp-proxy 构建任务，性能执行不以完整发布构建为前提。
- 当前两个 performance 工作流的 PR paths 未覆盖 `crates/**`；新需求必须覆盖 xp-proxy 与 xp-proxy-core 源码、crate manifest、
  锁文件及相关工具链/基准脚本，避免延续该遗漏。
- 现有产物名称不直接包含 commit SHA，也没有 proxy 专属 provenance manifest。

消费端需要通过可信 workflow run 和 manifest 校验绑定，禁止选择“最近一次成功”作为本次候选。

### 已收敛决定与工程验证边界

本轮确认轻量/全量环境与矩阵、三/六分钟设计预算、五/十分钟安全超时、双重性能门槛、准确 main 基线、独立上游构建、保守路径触发、仅豁免合并门禁的 PR label、main 持续测试、手动全量独
立报告、人工作废/恢复及来源校验、九十天留存。

没有按历史缺陷自动放行或自动作废的策略。

剩余工作属于实现与实测，不是隐含的新业务选择：在合同内确定完整 manifest schema、路径清单、CPU 分配、测量统计和资源回收方法；证明短采样窗口是否足够、产物下载与预热预算是否可达、
Check 与操作记录的关联是否可信，并补齐负例。

若实测无法满足预算或判定可靠性，必须明确暴露差距并重新讨论，不能暗改已经确认的门槛、覆盖或人工决定边界。

需求最终确认后才进入实施；本文件不授权本轮启动代码修复、工作流变更、合并、发布或部署。
